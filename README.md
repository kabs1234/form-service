# Конструктор анкет

Тестовое задание для карьерной платформы студентов. Менеджер сам собирает анкету на стажировку или мероприятие, публикует её по ссылке и смотрит ответы. Студент открывает ссылку и заполняет форму.

В задании была вторая проблема: студенты бросают анкеты на середине, и никто не знает почему. Под неё сделаны воронка заполнения, отчёт «на каком поле ушли» и автосохранение черновика.

## Запуск

Нужен Node.js 20 или новее. Больше ничего ставить не надо: базы данных, ключей и внешних сервисов нет.

```sh
npm install
npm start
```

Админка откроется на http://localhost:3000/admin. Первый `npm start` идёт дольше обычного, потому что перед запуском собирается фронтенд (`prestart` вызывает `vite build`).

Порт меняется переменной `PORT`:

```sh
PORT=4000 npm start            # bash
$env:PORT=4000; npm start      # PowerShell
```

Данные лежат в папке `data/` в корне проекта. Она создаётся при первом запуске и не попадает в git. Демо-данных нет: приложение стартует пустым, первую форму вы создаёте сами.

Для разработки есть `npm run dev`: Vite с горячей перезагрузкой и сервер в режиме watch. Vite проксирует `/api` на порт 3000.

## Основной сценарий

1. В `/admin` нажать «Новая форма», добавить вопросы. Типы полей: короткий текст, длинный текст, email, число, выпадающий список, один вариант, несколько вариантов, дата. Порядок меняется кнопками вверх/вниз, справа живое превью.
2. Опубликовать форму и скопировать ссылку вида `/f/xxxxxxxx`.
3. Открыть ссылку как студент, заполнить, отправить.
4. Вернуться в админку: ответ появился в таблице ответов, сессия — в аналитике.

Форму можно править и после того, как пришли ответы. Если вопрос удалён, его колонка в таблице остаётся: каждый ответ хранит тексты вопросов на момент отправки, поэтому колонка подписана старым текстом вопроса. Для ответов, сохранённых до этого изменения, колонка называется «(удалённое поле)».

## Как устроена аналитика отказов

Публичная форма отправляет на сервер четыре события:

| Событие        | Когда                                                              |
| -------------- | ------------------------------------------------------------------ |
| `view`         | форма загрузилась (один раз)                                       |
| `start`        | студент впервые что-то ввёл (один раз)                             |
| `field_focus`  | фокус или ввод перешёл на другое поле, не то, что было последним   |
| `submit`       | ответ успешно отправлен (один раз)                                 |

События уходят через `fetch` с `keepalive: true`, чтобы запрос не оборвался, если студент закрывает вкладку. Идентификатор сессии генерируется при открытии и хранится в `sessionStorage`.

Из этих событий сервер считает две вещи.

**Воронку.** Сколько уникальных сессий открыли форму, сколько начали заполнять и сколько отправили, плюс конверсия между шагами. Отсюда видно, где основная потеря: люди не начинают или начинают и бросают.

**Последнее поле перед уходом.** Берутся брошенные сессии (был `start`, не было `submit`), и для каждой — поле из последнего `field_focus`. Количество по полям показывается столбчатой диаграммой, лидер подсвечен: «X% бросивших остановились на этом поле».

Сначала я думал считать, сколько людей заполнило каждое поле по порядку, как в классической воронке. От этого отказался: студенты пропускают необязательные поля и заполняют форму не сверху вниз, и такая воронка показывает отвалы там, где их нет. Последнее поле, на котором человек был перед уходом, честнее отвечает на вопрос «где застревают».

У `sessionStorage` есть минус: сессия живёт, пока открыта вкладка. Если студент закрыл вкладку и вернулся завтра, черновик восстановится, но в аналитике это будут две сессии, и первая засчитается как брошенная.

## Решения и компромиссы

**JSON-файл и очередь записи.** Формы и ответы хранятся в `data/db.json`. При старте файл читается в память, изменения идут в памяти, а запись на диск проходит через одну очередь промисов, так что две записи никогда не пересекаются. Без очереди два одновременных ответа могли бы записать файл наперегонки, и один из них потерялся бы. Если запись упала, очередь не блокируется и следующие записи проходят.

**Атомарная запись.** Новое содержимое сначала пишется во временный `db.json.tmp`, потом `fs.rename` заменяет им `db.json`. Если процесс упадёт посреди записи, на диске останется старый целый файл, а не обрезанный.

**События отдельно, только дописыванием.** Аналитика пишется в `data/events.jsonl`, по одному JSON-объекту на строку, через `fs.appendFile`. Файл никогда не перезаписывается целиком. Событий намного больше, чем ответов, и гонять их через общую очередь `db.json` незачем.

Весь доступ к файлам собран в [server/storage.ts](server/storage.ts), чтобы хранилище можно было заменить на настоящую БД, не трогая маршруты.

**Валидация на сервере.** Схемы zod лежат в `/shared` и общие для клиента и сервера. Для каждой отправки сервер строит схему из полей конкретной формы: обязательность, формат email, число, дата, допустимые варианты для списков, без повторов в чекбоксах, без лишних ключей. Клиентской проверке сервер не доверяет. События тоже проверяются: принимаются только для опубликованных форм, `fieldId` должен принадлежать форме. Неизвестная ссылка и неопубликованная форма возвращают одинаковый 404, чтобы по ответу нельзя было понять, существует ли черновик.

**Ссылка отдельно от ID.** У формы есть внутренний ID и публичный slug из 8 символов (`crypto.randomBytes(6)` в base64url). Ссылку можно перевыпустить кнопкой в конструкторе: старая перестанет работать, а ответы и аналитика останутся привязаны к форме. При генерации slug проверяется на совпадение с существующими.

**Все пакеты в `dependencies`.** Включая Vite, Tailwind, TypeScript и tsx. `npm start` сначала собирает фронтенд, а при `NODE_ENV=production` npm не ставит `devDependencies`, и сборка бы сломалась. В `devDependencies` остались только ESLint и его плагины: они требуют Node 20.9+, но для `npm start` не нужны. На Node 20.0–20.8 `npm install` выведет предупреждение EBADENGINE, на запуск это не влияет.

**Vite закреплён на 6.** Vite 7 требует Node 20.19+, а задание требует любой Node 20. По той же причине `@vitejs/plugin-react` взят версии 4, а Rollup закреплён на 4.62.3 через `overrides`: начиная с 4.62.4 у него появилась опциональная зависимость, которая требует Node 22.20 и даёт предупреждение при установке на Linux с Node 20.

**Ничего не компилируется при установке.** Поэтому SQLite не подошёл: `better-sqlite3` собирается через node-gyp, а встроенный `node:sqlite` есть только в Node 22+.

## Что сознательно не делал

- Авторизацию админки. По заданию `/admin` открыт.
- Многостраничные формы и условную логику. Сильно усложняют и конструктор, и аналитику, а для анкеты на стажировку хватает одной страницы.
- Перетаскивание полей. Кнопки вверх/вниз проще, работают с клавиатуры и на телефоне.
- Загрузку файлов, темы оформления, уведомления на почту.
- Версионирование полей. Вместо него ответ хранит тексты вопросов на момент отправки, этого хватает, чтобы читать старые ответы после правок формы.

## Что изменилось бы в продакшене

- Postgres вместо JSON-файлов: транзакции, индексы, и не нужно держать все данные в памяти и перечитывать весь `events.jsonl` при открытии аналитики.
- Вход для менеджеров.
- Ограничение частоты запросов на публичных эндпоинтах, особенно на событиях: сейчас кто угодно может накрутить воронку.
- Сессия аналитики, которая переживает закрытие вкладки, чтобы вернувшийся студент не считался бросившим.

## Структура

```
server/       Express: маршруты API, хранилище, расчёт аналитики
src/          React: админка и публичная форма
shared/       схемы zod и типы, общие для клиента и сервера
data/         db.json и events.jsonl, создаётся при запуске
docs/ai-log/  логи сессий с ИИ-ассистентом
```

Стек: Express 5 и TypeScript (запуск через tsx), React с React Router, Vite 6, Tailwind v4, shadcn/ui на Radix, react-hook-form, zod, Recharts для графиков.
