  shared/form.ts: the form definition

  - FIELD_TYPES: the eight field types as one as const list. It drives z.enum
    and the FieldType type, so the list exists in only one place.
  - fieldSchema: one field. Labels and options are trimmed. A refine rule
    requires at least one option for select, radio and checkbox fields. Options
    must be unique, or a student couldn't tell two identical ones apart.
  - fieldsSchema: the field list. Field IDs must be unique because answers are
    keyed by field ID.
  - formInputSchema: what the admin sends on create and update (title,
    description, fields, published). The client never sends id, slug or
    timestamps; the server creates them. That stops a client from picking its
    own slug.
  - formSchema: the stored form, built by adding those server-owned fields to
    formInputSchema with .extend(...).

  shared/response.ts: validating a submission

  buildAnswersSchema(fields) builds a zod schema from a form's field list. The
  public form will use it through react-hook-form, and the server will run it
  again on submit, so both sides check the same rules.
  - Answers are always strings, and checkbox answers are string[]. That's
    exactly what HTML inputs produce, so the schema's input and output have the
    same shape. That's why the client's parsed result passes the server's check
    again (the smoke test showed this).
  - Empty means '' or []. A required field rejects empty values with "This field
    is required". An optional field accepts them. If an optional key is missing
    entirely, it defaults to '' or [], so every stored response has the same
    keys.
  - Per-type rules live in answerRuleFor, one switch over the field type:
    - email: zod's built-in email regex
    - number: a number pattern
    - date: YYYY-MM-DD
    - select/radio: the answer must be one of the options

    Checkbox answers must each be one of the options.
  - z.strictObject rejects answers keyed by a field the form doesn't have, so
    nobody can store junk keys.

  shared/event.ts: analytics events

  - eventInputSchema is a discriminated union, meaning zod picks the variant by
    the type value. A field_focus event must include a fieldId; view, start and
    submit events have none. The server will also check that the fieldId belongs
    to the form, because that needs the form itself.
  - analyticsEventSchema is the stored event: the input plus formId and ts, both
    added by the server. It lets us validate each line read back from
    events.jsonl.

  Two decisions to check

  1. Number answers are stored as validated strings, e.g. "21", not as numbers.
     Nothing calculates with them, and this keeps "same schema, same shape on
     both sides" true. The alternative is converting to a number in the schema.
     Then the server would have to accept both strings and numbers, because the
     client sends what the schema outputs. Tell me if you'd prefer that.
  2. The Response and Event types are named FormResponse and AnalyticsEvent.
     Plain Response and Event would clash with the browser's built-in Response
     and Event types.
